# P4 Semantic Diff Planner and Offline Dry Run

## Status

The project now has a complete **offline semantic planning path** from beginner template input through current/desired comparison and exportable dry-run evidence.

Device write authority remains **FALSE**.

No module in this milestone generates Cisco CLI or connects to a device.

## Normalized current state

The planner does not compare desired intent against raw CLI text.

`CurrentNetworkState` uses typed state:

```text
CurrentVLANState
CurrentAccessPortState
CurrentTrunkState
CurrentManagementState
satisfied_security_rules
```

A future read-only collector must normalize live switch evidence into these structures.

### Current-state basis

Absence has different meaning depending on evidence quality:

```text
blank_design
observed_complete
observed_partial
```

`blank_design` means a deliberate green-field design where absence is authoritative.

`observed_complete` means the read-only collector has proved completeness for the planner's managed scope.

`observed_partial` means absence is **not** authoritative. The planner may show candidate differences but marks absence-dependent operations `blocked_current_state` and blocks provider readiness.

This prevents a partial collector failure from being interpreted as "the switch does not have this configuration".

## Typed semantic operations

Current operation types:

```text
CreateVlan
UpdateVlan
ConfigureL3Interface
AssignAccessPort
ConfigureTrunk
SetAllowedVlans
SetManagementPolicy
ApplySecurityPolicyRule
```

These are semantic operations only.

A `CreateVlan` object describes the desired VLAN identity. It does not contain or imply a Cisco command string.

Each operation contains:

```text
operation_id
operation_type
target
risk_class
readiness
dependencies
before
desired
capability_requirements
verification
rollback metadata
destructive=false
device_commands_generated=false
```

## Stable operation IDs

Operation IDs are derived deterministically from:

```text
operation_type + target + desired state
```

using canonical JSON and SHA-256.

The same semantic operation therefore retains the same ID across repeated planning runs.

## Stable plan hash

The complete semantic plan has a SHA-256 `plan_hash` over canonical plan content.

The hash includes:

- current-state evidence basis;
- typed operations;
- dependencies;
- readiness;
- before/desired values;
- capability requirements;
- verification/rollback metadata;
- plan issues;
- preserved current objects;
- safety flags.

It does not include an execution token or credential.

## Dependency graph

Dependencies are explicit IDs, not implicit command ordering.

Examples:

```text
CreateVlan(120)
   -> AssignAccessPort(GE9, VLAN 120)

CreateVlan(120)
   -> ConfigureTrunk(XG1 carrying VLAN 120)

CreateVlan(management VLAN)
ConfigureTrunk(management VLAN)
   -> SetManagementPolicy
```

L3 interface intent depends on VLAN creation when the VLAN is new.

A future provider/compiler must preserve this dependency graph rather than inventing its own unsafe order.

## Risk classes

The planner uses repository risk classes.

Current examples:

```text
CreateVlan             W1
UpdateVlan             W1
ConfigureL3Interface   W2
AssignAccessPort       W2
ConfigureTrunk         W2
SetAllowedVlans        W2
SetManagementPolicy    W2
Security rule          rule-defined W1/W2
```

The dry run provides a consolidated risk summary:

```text
risk counts
highest risk
connectivity-impacting operation IDs
destructive operation IDs
future safety gate required
```

No operation generated by the current planner is destructive.

## Capability readiness

Operation readiness is separate from the existence of an operation in the dry run.

```text
ready
blocked_capability
blocked_current_state
policy_only
```

A user can therefore see what the desired design would require without the system pretending that the operation is ready to compile or execute.

For example, the current exact CBS250 profile has many features in `documented_not_observed` state. The planner retains those desired changes in the dry run but marks them capability-blocked.

## No implicit removal

The planner is conservative by design:

```text
implicit_removals = false
```

Current VLANs, interfaces, L3 state, management policy, or security rules that are outside the desired managed scope are listed in:

```text
preserved_current_objects
```

They are not silently removed.

A future explicit removal workflow must have separate ownership, scope, impact analysis, and safety policy.

## Verification contract

Every semantic operation carries a verification method and expected state.

Examples:

```text
observe_vlan_identity
observe_vlan_l3_interface
observe_access_port_membership
observe_trunk_membership
observe_management_reachability_and_policy
verify_normalized_security_rule
```

These are semantic verification requirements, not CLI commands.

A future CBS250 provider must map them to reviewed read-only evidence collectors.

## Rollback metadata

The planner stores before-state where authoritative.

For changes to an existing object, rollback metadata can state:

```text
restore_before_state
```

For creation or control-specific security changes, the P4 planner deliberately does not invent a delete/reversal procedure. It uses provider-defined or not-automatically-defined rollback metadata.

This prevents the planner from creating an unsafe rollback simply because one looks syntactically symmetrical.

## Idempotency

If `CurrentNetworkState` already matches the desired intent and the relevant security compliance state is recorded, the planner returns:

```text
operations = []
status = NO_CHANGES
```

Repeated identical input produces identical operation IDs, plan hash, JSON, and text output.

## Management impact summary

Management-affecting operations are identified separately.

The analysis considers at least:

- management VLAN creation/change;
- management VLAN L3 changes;
- management VLAN access-port changes;
- trunks carrying the management VLAN;
- management policy changes;
- management security-policy rules.

Output includes:

```text
management_vlan_id
affected_operation_ids
affected_targets
blocked_operation_ids
status
lockout_analysis_complete=false
safe_to_apply=false
```

The P4 impact analyzer **never** declares a management change safe to apply.

That judgment belongs to the future P6 lockout engine, which must prove continued reachability or an approved recovery path.

## Export bundle

`export_dry_run_bundle()` writes deterministic local evidence:

```text
network_dry_run.json
network_dry_run.txt
manifest.json
```

`manifest.json` contains:

- export schema version;
- dry-run status;
- semantic plan hash;
- SHA-256 and byte length for JSON/text files;
- `execution_authority=false`;
- `device_commands_generated=false`.

The export model has no username/password/private-key fields.

## What remains outside P4 planner authority

This milestone does not provide:

- a CBS250 command compiler;
- free-form CLI input;
- an SSH executor;
- management lockout proof;
- live-write authorization;
- startup-config persistence;
- implicit or autonomous destructive cleanup.

## Next architectural boundary

The next engineering work can proceed in two parallel safe lanes:

1. **P2 read-only collector**: normalize exact live CBS250 current state into `CurrentNetworkState`.
2. **P5 compile-only provider foundation**: map only live-proven typed operations into reviewed CBS250 syntax, still with no executor and write authority FALSE.

P5 must not be allowed to bypass missing P1 evidence. Unknown or merely documented-but-unobserved capabilities remain compile-blocked.
